# Architecture Decision Records — Ravand

این فایل تصمیم‌های مهم فنی را ثبت می‌کند. هر تصمیم جدید با تاریخ و دلیل اضافه می‌شود؛ تصمیم‌های قبلی حذف نمی‌شوند، فقط با «Superseded» علامت می‌خورند.

قالب: `ADR-<شماره> — <عنوان>` / وضعیت / تاریخ / زمینه / تصمیم / پیامد.

---

## ADR-001 — معماری Modular Monolith

- **وضعیت:** پذیرفته‌شده
- **تاریخ:** 2026-11-25
- **زمینه:** MVP با یک فروشنده و حجم داده کوچک؛ microservice هزینه و پیچیدگی عملیاتی بی‌دلیل ایجاد می‌کند.
- **تصمیم:** یک اپلیکیشن Laravel واحد با تفکیک ماژول‌های دامنه‌ای در `app/Domain/*`. مرزها منطقی‌اند، نه شبکه‌ای.
- **پیامد:** استقرار ساده؛ در آینده اگر ماژولی واقعاً نیاز به استخراج داشت، مرزها از قبل مشخص است.

## ADR-002 — Bootstrap با Laravel 13 + Vue starter kit رسمی

- **وضعیت:** پذیرفته‌شده
- **تاریخ:** 2026-11-25
- **زمینه:** مخزن خالی بود و سند، Laravel 13 + Vue 3 + TypeScript + Inertia + shadcn-vue می‌خواهد.
- **تصمیم:** استفاده از اسکلت رسمی Laravel (نسخه ۱۳) با فرانت Vue/Inertia/TypeScript و Tailwind. ساختار و packageهای رسمی حفظ می‌شوند و بازنویسی دستی انجام نشد.
- **پیامد:** مسیر ارتقا و مستندات رسمی در دسترس است؛ کدهای auth اولیه در فاز ۰۱ بازبینی و متناسب با مدل `tenant_user` اصلاح می‌شوند.

## ADR-003 — چندفروشگاهی از ابتدا: Shared DB + Shared Schema + `tenant_id`

- **وضعیت:** پذیرفته‌شده
- **تاریخ:** 2026-11-25
- **زمینه:** سند صریحاً tenant isolation را از روز اول می‌خواهد؛ ولی MVP فقط یک فروشگاه فعال دارد.
- **تصمیم:** ستون `tenant_id` از ابتدا در جداول دامنه‌ای، scope اجباری در سرور، و ممنوعیت اتکا به `tenant_id` ارسالی کلاینت. تشخیص tenant از membership معتبر کاربر.
- **پیامد:** پیاده‌سازی فازهای بعدی باید هر Query و Policy را tenant-safe نگه دارد؛ لاگ/تست‌های بین‌مستاجری الزامی است.

## ADR-004 — شناسه‌ها: ULID برای رکوردهای عمومی، شماره نمایشی جدا

- **وضعیت:** پذیرفته‌شده
- **تاریخ:** 2026-11-25
- **زمینه:** شناسه عددی ترتیبی نشت اطلاعات و شمارش را آسان می‌کند؛ از طرفی کاربر به شماره نمایشی خوانا نیاز دارد.
- **تصمیم:** `id` از نوع ULID (رشته ۲۶ کاراکتری) برای موجودیت‌های دامنه‌ای؛ شماره نمایشی `CUS-000001` و `ORD-000001` جدا و یکتا در محدوده tenant.
- **پیامد:** مهاجرت جداول دامنه‌ای از فاز ۰۱ به بعد باید ULID را پیش‌فرض بگیرد (جداول پیش‌فرض `users` در فاز ۰۱ بازبینی می‌شود).

## ADR-005 — تاریخ: ذخیره میلادی/UTC، نمایش و ورود شمسی

- **وضعیت:** پذیرفته‌شده
- **تاریخ:** 2026-11-25
- **زمینه:** MySQL و ابزارهای تحلیل با تاریخ میلادی بهتر کار می‌کنند؛ کاربر فارسی به تقویم شمسی نیاز دارد.
- **تصمیم:** ذخیره `DATETIME` میلادی (UTC) و `DATE` میلادی برای تاریخ تقویمی؛ تبدیل فقط در یک Date Adapter مرکزی (فاز ۰۲). timezone پیش‌فرض tenant: `Asia/Tehran`.
- **پیامد:** هیچ منطق تبدیل تاریخ در فرم‌های پراکنده نوشته نمی‌شود.

## ADR-006 — پول: `DECIMAL(20,0)` + `currency_code` snapshot

- **وضعیت:** پذیرفته‌شده (پیاده‌سازی در فاز ۰۳)
- **تاریخ:** 2026-11-25
- **زمینه:** ریال/تومان عدد صحیح هستند و float خطای گردکردن ایجاد می‌کند؛ تغییر ارز tenant نباید اسناد قدیمی را تغییر دهد.
- **تصمیم:** مبالغ `DECIMAL(20,0)` بدون اعشار؛ هر رکورد مالی `currency_code` (`IRR`/`IRT`) خودش را snapshot می‌کند؛ محاسبه در Money Value Object مرکزی و سمت سرور.
- **پیامد:** مجموع سفارش هرگز از مبلغ ارسالی مرورگر گرفته نمی‌شود.

## ADR-007 — MySQL 8.4 LTS به‌عنوان موتور هدف، MariaDB 10.4 در محیط توسعه فعلی

- **وضعیت:** پذیرفته‌شده با ریسک ثبت‌شده
- **تاریخ:** 2026-11-25
- **زمینه:** سند MySQL 8.4 LTS می‌خواهد. Docker روی ماشین توسعه نصب نیست و مالک محصول تصمیم گرفت از XAMPP استفاده کند؛ XAMPP نصب‌شده MariaDB **10.4.32** دارد (نه MySQL 8.4).
- **تصمیم:** کد و migrationها فقط از قابلیت‌های مشترک MySQL 8.4/MariaDB 10.4 استفاده می‌کنند (بدون `CHECK` پیچیده، بدون generated column وابسته به نسخه، بدون collation اختصاصی MySQL 8). `docker-compose.yml` با `mysql:8.4` برای محیط استاندارد ارائه می‌شود تا انتقال بدون تغییر کد ممکن باشد.
- **پیامد:** تفاوت‌های نسخه (به‌ویژه collation و رفتار JSON) باید در فازهای بعدی هنگام نوشتن Query بررسی شود. پیش از production، مهاجرت به MySQL 8.4 الزامی است.

## ADR-008 — Collation: `utf8mb4_unicode_ci`

- **وضعیت:** پذیرفته‌شده
- **تاریخ:** 2026-11-25
- **زمینه:** MySQL 8 پیش‌فرض `utf8mb4_0900_ai_ci` دارد، اما MariaDB 10.4 آن را نمی‌شناسد و migration در محیط توسعه شکست می‌خورد.
- **تصمیم:** `charset=utf8mb4` و `collation=utf8mb4_unicode_ci` در config دیتابیس و compose. جستجوی فارسیِ مقاوم به «ی/ي» و «ک/ك» از طریق ستون normalized در فاز ۰۲ انجام می‌شود، نه با اتکا به collation.
- **پیامد:** رفتار جست‌وجو بین MySQL و MariaDB یکسان‌تر می‌شود؛ نرمال‌سازی در کد (سرویس مشترک) منبع حقیقت است.

## ADR-009 — Queue/Cache/Session روی driver دیتابیس در MVP

- **وضعیت:** پذیرفته‌شده
- **تاریخ:** 2026-11-25
- **زمینه:** سند Redis را الزام نکرده و می‌خواهد اجرای محلی ساده باشد.
- **تصمیم:** `QUEUE_CONNECTION=database`, `CACHE_STORE=database`, `SESSION_DRIVER=database`؛ همه از طریق config قابل تعویض می‌مانند.
- **پیامد:** وابستگی زیرساختی کمتر؛ در صورت رشد، Redis بدون تغییر کد business اضافه می‌شود.

## ADR-010 — بدون AI داخلی در MVP

- **وضعیت:** پذیرفته‌شده
- **تاریخ:** 2026-11-25
- **زمینه:** سند صریحاً هر اتصال به LLM/embedding را از MVP حذف کرده؛ هدف فقط داده آماده برای ابزارهای خارجی است.
- **تصمیم:** هیچ SDK/کلید/فراخوانی AI اضافه نمی‌شود؛ فقط قرارداد داده و export در فاز ۰۵.
- **پیامد:** هر پیشنهاد افزودن AI در بازبینی رد می‌شود تا فاز ۰۵ و تصمیم محصول بعدی.

## ADR-011 — افزونه‌های UI: shadcn-vue با کپی درون مخزن

- **وضعیت:** پذیرفته‌شده
- **تاریخ:** 2026-11-25
- **زمینه:** UI باید مینیمال، سفید/مشکی و قابل سفارشی‌سازی باشد؛ کتابخانه سنگین با استایل غالب مطلوب نیست.
- **تصمیم:** کامپوننت‌های shadcn-vue داخل `resources/js/components/ui` نگهداری می‌شوند و design tokenها (سفید/مشکی) در یک لایه مرکزی تعریف می‌شوند؛ رنگ‌ها در ده‌ها فایل تکرار نمی‌شوند.
- **پیامد:** کنترل کامل روی ظاهر بدون فورک کردن کتابخانه.
